Resetting Offsets

Control exactly where consumption begins — replay from the start, or skip the backlog and listen live.

1. Two Properties Govern Starting Position

When an application starts, its initial position in each assigned partition depends on two binding-level consumer properties:

PropertyDefaultRole
startOffsetearliest (named group) / latest (anonymous)Where to start when there is no committed offset
resetOffsetsfalseWhether to ignore the committed offset and seek to startOffset anyway

2. Default Behavior: resetOffsets=false

When resetOffsets is false, normal Kafka auto.offset.reset semantics apply. The critical question is: is there a committed offset for this consumer group on this partition?

  • Committed offset exists → resume from that offset (the normal, expected case for a running app).
  • No committed offset exists → use startOffset to decide.
The default startOffset depends on whether you set a group:
  • Binding with an explicit group → defaults to earliest (reads existing messages)
  • Anonymous binding (no group) → defaults to latest (only new messages)
This is why a brand-new named consumer group replays the backlog, but an anonymous consumer starts fresh from now.

3. When Does "No Committed Offset" Happen?

Two common conditions create a situation with no committed offset:

  1. First-ever startup with a particular consumer group — nothing has been committed yet.
  2. Offset expired. With modern brokers (2.1+, default broker props), offsets are expired 7 days after the last member leaves the group (see the offsets.retention.minutes broker property). An idle app whose group sat empty for a week loses its place.

4. resetOffsets=true: Force a Seek

When resetOffsets is true, the binder ignores any current committed offset and seeks each newly assigned partition to the position dictated by startOffset — as if this binding has never consumed from the topic before.

startOffsetEffect of resetOffsets=trueUse case
earliestseekToBeginning on all new partitionsConsume from a compacted topic (replay the current key/value state)
latestseekToEnd on all new partitionsConsume an event topic where you only care about events from now on

5. A Concrete Application

spring:
  cloud:
    stream:
      bindings:
        stateConsumer-in-0:
          destination: compacted-state
          group: state-reader
      kafka:
        bindings:
          stateConsumer-in-0:
            consumer:
              startOffset: earliest
              resetOffsets: true   # re-seek to beginning on every start

Every time this app starts, it performs seekToBeginning — ideal for rebuilding an in-memory snapshot from a compacted topic that holds the latest value per key.

6. Two Important Caveats

1. Rebalance behavior. If a rebalance occurs after the initial assignment, the seeks are performed only on newly assigned partitions — not partitions already assigned at startup. Partitions you already held keep their position.
2. Conflict with rebalance listeners. If you provide a KafkaBindingRebalanceListener for manual offset control, you must not set resetOffsets=true — it will cause an error. For full manual control, use the rebalance listener instead of resetOffsets.

Assessment

Retrieval Practice:

1. Name the two properties that govern starting position, and state the role of each (one decides where, the other decides whether to honor it).

2. With resetOffsets=false, what happens when a committed offset exists versus when none exists? What are the default startOffset values for a named group vs. an anonymous binding?

3. Name the two conditions under which no committed offset exists for a consumer group, and which broker property controls offset expiration.

4. With resetOffsets=true and startOffset=earliest, what seek operation runs, and what is a realistic use case for it?

5. State the two caveats: what happens to seeks after a rebalance, and why must resetOffsets=true not be combined with a KafkaBindingRebalanceListener?
