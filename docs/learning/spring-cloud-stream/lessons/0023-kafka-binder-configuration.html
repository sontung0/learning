Kafka Binder Configuration

Three namespaces, one mental model: binder-wide, per-consumer, per-producer. Know the defaults and you can configure almost anything.

1. The Three Configuration Namespaces

Kafka-specific properties live under the spring.cloud.stream.kafka prefix, in three distinct scopes. Each answers a different question:

NamespaceScopeAnswers
kafka.binder.*Binder-wide — all clients"What broker am I connecting to? How are topics auto-created?"
kafka.bindings.<name>.consumer.*Per consumer binding"How does this consumer commit offsets, handle errors, reset?"
kafka.bindings.<name>.producer.*Per producer binding"Does this producer set keys, compress, run sync?"
Namespace rule: portable properties (destination, group, content-type) live in the core stream.bindings.* namespace (Lesson 0016). Kafka-only properties live in the kafka.bindings.* namespace — never mix them.

You can also set a default across all channels: spring.cloud.stream.kafka.default.consumer.<property>=<value> or ...default.producer... — avoiding repetition when all bindings share a Kafka-specific setting.

2. Binder-Wide Properties (The Essentials)

PropertyDefaultWhat it does
brokerslocalhostBroker addresses (comma-separated; host or host:port)
defaultBrokerPort9092Port used when brokers omits a port
autoCreateTopicstrueBinder creates topics if they don't exist. If false, binder fails to start on a missing topic
autoAddPartitionsfalseIf true, binder increases partition count when needed. If false and topic has too few partitions, binder fails to start
minPartitionCount1Minimum partitions on auto-created topics; superseded by larger of producer partitionCount or instanceCount × concurrency
replicationFactor-1Replicas for auto-created topics. -1 = use broker's default.replication.factor
requiredAcksallProducer acks setting (maps to Kafka acks)
Topic provisioning gotcha: if autoAddPartitions is false (the default) and an existing topic has fewer partitions than the binder expects (max of minPartitionCount or partitionCount), the binder fails to start. This is a very common startup failure — know where to look.

2.5. Client Property Maps

Three map properties let you pass raw Kafka client properties straight through:

PropertyApplies toNotes
kafka.binder.configurationBoth producers & consumersUse for common client settings (e.g. security). Unknown props are filtered out here
kafka.binder.consumerPropertiesAll consumersUnknown consumer props are allowed; supersedes configuration
kafka.binder.producerPropertiesAll producersUnknown producer props are allowed; supersedes configuration

At the per-binding level, each consumer/producer also has its own configuration map for that binding alone.

3. Consumer Properties (The Essentials)

PropertyDefaultWhat it does
autoRebalanceEnabledtrueWhen false, partitions are fixed via instanceCount/instanceIndex (Lesson 0019)
autoCommitOffsettrueCommit offsets after processing. false → manual ack via kafka_acknowledgment header. Deprecated since 3.1 — prefer ackMode
ackMode—Spring Kafka AckMode enum (replaces autoCommitOffset/ackEachRecord)
startOffsetearliest*Where a new group begins: earliest or latest. *Named group defaults to earliest; anonymous group defaults to latest
resetOffsetsfalseReset consumer offsets to startOffset on startup. Must be false if a rebalance listener is provided
enableDlqfalseSend failed records to a dead-letter topic (default name error.<destination>.<group>)
dlqNamenullCustom DLQ topic name
Start offset defaults matter. A consumer in a named group (set group) starts at earliest — it reads existing messages. An anonymous consumer (no group) starts at latest — it sees only messages arriving after it connects. This is a frequent source of "where did my messages go?" confusion.

4. Producer Properties (The Essentials)

PropertyDefaultWhat it does
messageKeyExpressionnoneSpEL to set the Kafka message key (e.g. headers['myKey']). To pass through the incoming key: headers['kafka_receivedMessageKey']
syncfalseSynchronous sends — wait for ack per send (slower, safer order)
compressionnonenone, gzip, snappy, lz4, or zstd
headerPatterns*Which Spring messaging headers map to Kafka headers (e.g. !secret,*); id and timestamp are never mapped
useTopicHeaderfalsetrue → override destination with the KafkaHeaders.TOPIC header per-message (dynamic topic routing)
recordMetadataChannelnullChannel to receive RecordMetadata (offset/partition) for successful sends

5. Topic Property Maps Everywhere

Both consumer and producer bindings expose topic.properties, topic.replication-factor, and topic.replicas-assignment — used when the binder provisions (auto-creates) a topic. These override binder-wide settings for a single binding.

Assessment

Retrieval Practice:

1. Name the three Kafka configuration namespaces and the scope of each (binder-wide, per-consumer, per-producer). Where do portable properties like destination and group live instead?

2. What are the defaults for autoCreateTopics, autoAddPartitions, and minPartitionCount? Describe the scenario where these defaults cause the binder to fail at startup.

3. What is the difference between the three client-property maps (configuration, consumerProperties, producerProperties) in terms of which clients they affect and whether unknown properties are filtered?

4. What is the default startOffset for a consumer in a named group vs an anonymous group? Why does this matter in practice?

5. Name three producer properties and their defaults. Which property would you set to route messages to a per-message dynamic topic?
