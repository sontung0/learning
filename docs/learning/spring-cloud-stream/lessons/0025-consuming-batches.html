Consuming Batches

Process a whole poll's worth of records at once — higher throughput, but with sharper edges around retries, DLQ, and tracing.

1. The Switch: batch-mode

By default, Spring Cloud Stream hands each Kafka record to your function one at a time. Setting batch-mode to true changes that — all records received in a single Consumer.poll() are delivered to your function as a single List. This is a portable binding property on the core namespace:

spring:
  cloud:
    stream:
      bindings:
        myConsumer-in-0:
          consumer:
            batch-mode: true
What controls batch size? It's not a Spring Cloud Stream property — it's governed by the raw Kafka consumer properties max.poll.records, fetch.min.bytes, and fetch.max.wait.ms (set via the consumer's configuration map from Lesson 0023). Spring Cloud Stream just decides whether to hand you the whole poll at once or record-by-record.

2. Allowed Type Signatures

When batch mode is on, your function receives a List. Two signatures are permitted:

SignatureHeaders?When to use
Consumer<List<Person>>No — no headers availableWhen you only need the payload objects
Consumer<Message<List<Person>>>Yes — but each header value is itself a CollectionWhen you need per-record headers aligned to payloads

3. The Per-Record Header Alignment

This is the subtle part. Suppose your Message contains a list of ten Person objects. The MessageHeaders are not a single value — each header key maps to a list, where position i corresponds to payload element i. You must iterate in lockstep:

@Bean
public Consumer<Message<List<Person>>> processPeople() {
    return message -> {
        List<Person> people = message.getPayload();
        List<String> keys = message.getHeaders()
                .get("kafka_receivedMessageKey", List.class);
        for (int i = 0; i < people.size(); i++) {
            handle(people.get(i), keys.get(i));  // aligned by index
        }
    };
}
Forbidden signature: List<Message<Person>> is not allowed in batch mode. You cannot get a list of individually-wrapped messages — use Message<List<...>> instead.

4. KafkaNull (Tombstones) in Batches

When the topic contains KafkaNull objects (tombstone records), the received list contains a null element at the corresponding position — for both List<Person> and Message<List<Person>> signatures. Your handler must null-check each element.

5. Retries Are Disabled — Plan for It

Binder retry is not supported in batch mode. maxAttempts is overridden to 1. For retry-like behavior, use one of:
  • A DefaultErrorHandler via a ListenerContainerCustomizer (Spring for Apache Kafka)
  • Manual AckMode + Acknowledgment.nack(index, sleep) — commits offsets for the processed portion of the batch and redelivers the remainder

6. DLQ in Batch Mode (4.0.2+)

Starting with version 4.0.2, the binder supports dead-letter queues while consuming in batch mode. But the granularity is coarse: all records from the previous poll are sent to the DLQ topic — not just the individual record that failed. If you need finer control, use the nack(index, sleep) technique above to isolate the failing record.

7. Observability Caveat

Tracing propagation is not directly supported in batch listeners — the underlying Spring for Apache Kafka library only traces record listeners. This makes sense: a batch may contain records from multiple topics, partitions, and producers with no guaranteed correlation, so the framework cannot assume a single trace ID. If you use Message<List<...>>, the header kafka_batchConvertedHeaders includes tracing headers per record — but you must iterate and start observations manually.
