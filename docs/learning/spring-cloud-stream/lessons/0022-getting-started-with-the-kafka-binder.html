Getting Started with the Kafka Binder

Add the dependency, and see how Spring Cloud Stream's abstractions map cleanly onto Kafka's native concepts.

1. Adding the Kafka Binder

You now enter Phase 5: the Apache Kafka Binder — the most widely used binder in production. To use it, add one of two Maven dependencies:

<!-- Option A: the binder artifact directly -->
<dependency>
    <groupId>org.springframework.cloud</groupId>
    <artifactId>spring-cloud-stream-binder-kafka</artifactId>
</dependency>

<!-- Option B: the Spring Cloud Stream Kafka Starter -->
<dependency>
    <groupId>org.springframework.cloud</groupId>
    <artifactId>spring-cloud-starter-stream-kafka</artifactId>
</dependency>
Which one? Both pull in the same Kafka binder. The spring-cloud-starter-stream-kafka starter is the conventional choice for new applications — it is the Spring Boot-style starter that transitively brings in everything you need. The spring-cloud-stream-binder-kafka artifact is the bare binder if you want finer control over what's on the classpath.

2. The Concept Mapping

One of the reasons the Kafka binder is so natural to use: Spring Cloud Stream's core abstractions map directly onto Kafka's native concepts. There is no impedance mismatch to bridge.

Spring Cloud Stream conceptApache Kafka concept
DestinationKafka topic
Consumer groupKafka consumer group (identical concept)
PartitionKafka partition (identical concept)

The binder implementation maps each destination to a Kafka topic. The consumer group maps to the same Kafka concept. Partitioning maps directly to Kafka partitions.

3. What This Means in Practice

Because of this direct mapping, everything you learned in Phases 1–4 transfers cleanly:

  • The functional programming model (Supplier, Function, Consumer) works unchanged — you just set the binder on the classpath.
  • Consumer groups (Lesson 0003): set spring.cloud.stream.bindings.<name>-in-0.group=my-group, and it is a Kafka consumer group.
  • Partitioning (Lesson 0019): Kafka handles partition distribution natively via consumer rebalance by default — instanceCount/instanceIndex are typically not required unless you disable auto-rebalance.
  • Content type negotiation (Lesson 0017): the default application/json works out of the box.

4. Client Version & Broker Compatibility

The binder bundles the Apache Kafka kafka-clients library. The client can communicate with older brokers, but certain features depend on the broker version:

Broker versionFeature limitation
Earlier than 0.11.x.xNative headers are not supported
0.11.x.xThe autoAddPartitions property is not supported
Check your broker version. If you're targeting an older Kafka cluster, some binder features may silently not work. Modern Kafka brokers (2.x+) support all features.
