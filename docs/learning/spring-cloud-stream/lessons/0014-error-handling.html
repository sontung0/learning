Error Handling

Turn a failed message handler into deliberate recovery work, not silent data loss.

1. Start With the Failure's Shape

A consumer can fail because a dependency is briefly unavailable, because the message violates a business rule, or because the application has a defect. These do not deserve the same response.

FailureFirst responseWhy
Temporary database timeoutRetryA later invocation may succeed unchanged.
Malformed or invalid eventDo not retry; route for reviewThe same payload will fail again.
Unexpected application bugObserve, alert, preserve messageOperators need context and a recovery path.
Rule of thumb: retry a condition that can change; isolate a message whose meaning will not change by trying it again.

2. The Default Retry Boundary

For a message-handler exception, Spring Cloud Stream can retry processing through a consumer retry template. Its default is three attempts, with exponential backoff beginning at 1 second, capped at 10 seconds. Configure it on the consumer binding when the default does not fit the failure mode.

spring:
  cloud:
    stream:
      bindings:
        inventory-in-0:
          consumer:
            max-attempts: 5
            back-off-initial-interval: 500
            back-off-multiplier: 2.0
            retryable-exceptions:
              java.net.SocketTimeoutException: true
              com.example.InvalidInventoryEvent: false

max-attempts counts the original call too: a value of 5 means one initial attempt plus up to four retries. Use retryable-exceptions when exception type is the cleanest way to separate transient from permanent failure.

3. Error Channels Keep Handling In-Process

After a failed binding, Spring Cloud Stream publishes an ErrorMessage to an error channel. A binding-specific channel follows the pattern <bindingName>.errors; a global errorChannel can also observe errors. These channels are for application-local actions such as structured logging, metrics, or a compensating workflow.

@Bean
public Consumer<ErrorMessage> inventoryErrors() {
    return errorMessage -> {
        Throwable failure = errorMessage.getPayload();
        // Record context, alert, or trigger a compensating action.
    };
}
Do not confuse an error channel with a DLQ. An error channel exists inside this running application. It does not itself provide durable broker storage for a message that needs later investigation or replay.

4. DLQs Preserve Exhausted Failures

A binder-specific dead-letter queue (DLQ) or topic forwards a message after processing is exhausted, keeping the original failure available for operators or a dedicated recovery flow. Enable it through the binder configuration, not the generic binding properties.

# Kafka: default DLQ topic is error.<destination>.<group>
spring.cloud.stream.kafka.bindings.inventory-in-0.consumer.enable-dlq=true

# RabbitMQ: declare and bind a dead-letter queue automatically
spring.cloud.stream.rabbit.bindings.inventory-in-0.consumer.auto-bind-dlq=true

A DLQ is not a success state. It is an operational contract: monitor its growth, retain enough diagnostic context, fix the cause, and decide whether each message should be corrected and replayed or deliberately discarded.

Decision Drill

Assessment:

1. A payment provider returns a timeout. Which mechanism comes first, and what property controls the total number of handler calls?

2. An event is missing a required account ID. Why is retrying it a poor default, and where should you send it if it must be investigated later?

3. What is the binding-specific error-channel naming pattern, what does it carry, and why is it different from a DLQ?

4. Give the Kafka and RabbitMQ properties that enable a dead-letter destination for inventory-in-0.

5. For max-attempts: 5, how many retries occur after the first handler call?
