Partitioning

Guarantee that data with a common key always lands on the same consumer instance — for stateful processing, ordering, and locality.

1. Why Partition?

Partitioning ensures that messages sharing a common characteristic are processed by the same consumer instance. This is critical for stateful processing: in a time-windowed average calculation, all measurements from a given sensor must reach the same instance, or the window will be incomplete.

Spring Cloud Stream provides a common abstraction for partitioning that works whether the broker is natively partitioned (Kafka) or not (RabbitMQ). The broker topic/queue is viewed as structured into multiple partitions; producers route by key, consumers claim specific partitions.

Both ends must be configured. Partitioning is a contract between producer and consumer — configuring only one side is a common bug.

2. Configuring the Producer (Output Binding)

Three properties control outbound partitioning. You set one key strategy plus the partition count:

PropertyPurpose
partitionKeyExpressionSpEL expression evaluated against the outbound message to extract the key (e.g. headers.id)
partitionKeyExtractorNameName of a PartitionKeyExtractorStrategy bean when SpEL is insufficient
partitionCountNumber of partitions to split data across
 
spring.cloud.stream.bindings.func-out-0.producer.partitionKeyExpression=headers.id
spring.cloud.stream.bindings.func-out-0.producer.partitionCount=5

Once the key is calculated, the target partition is chosen as key.hashCode() % partitionCount by default — a value between 0 and partitionCount - 1.

3. Customizing Partition Selection

If the default hashCode() % partitionCount formula doesn't suit you, you can override the selector (the step that maps key → partition), independently of the key extractor:

PropertyPurpose
partitionSelectorExpressionSpEL evaluated against the key to pick the partition
partitionSelectorNameName of a PartitionSelectorStrategy bean
 
@Bean
public CustomPartitionSelectorClass customPartitionSelector() {
    return new CustomPartitionSelectorClass();
}
// spring.cloud.stream.bindings.func-out-0.producer.partitionSelectorName=customPartitionSelector
Two distinct extension points: the key extractor decides what to partition by; the selector decides which partition that key maps to. Don't conflate them.

4. Configuring the Consumer (Input Binding)

The consumer side declares itself partitioned and states its position in the fleet (from Lesson 0018):

spring.cloud.stream.bindings.uppercase-in-0.consumer.partitioned=true
spring.cloud.stream.instanceIndex=3
spring.cloud.stream.instanceCount=5

instanceCount is the total number of app instances sharing the partitioned data; instanceIndex must be unique across them, in the range 0 to instanceCount - 1. Each instance uses its index to identify which partition(s) it receives from.

5. Broker-Specific Behavior

BrokerAre instanceCount / instanceIndex required?Why
RabbitMQYesNo native partitioning — a queue is created per partition, named using the instance index
Kafka (autoRebalanceEnabled=true, default)NoKafka itself distributes partitions across instances via rebalance
Kafka (autoRebalanceEnabled=false)YesThe binder (not Kafka) assigns partitions; requires at least as many partitions as instances — useful for sticky partition-to-instance mapping
Sticky assignment: disabling Kafka auto-rebalance lets you pin a specific partition to a specific instance — desirable when a partition's data must always be processed by the same instance for state locality.

6. End-to-End Example

# --- Producer ---
spring.cloud.stream.bindings.sensor-out-0.producer.partitionKeyExpression=headers.sensorId
spring.cloud.stream.bindings.sensor-out-0.producer.partitionCount=5

# --- Consumer instance 2 of 5 ---
spring.cloud.stream.bindings.avg-in-0.consumer.partitioned=true
spring.cloud.stream.instanceIndex=2
spring.cloud.stream.instanceCount=5

All messages with the same sensorId hash to the same partition and thus reach the same consumer instance — so the windowed average for each sensor is computed correctly.
