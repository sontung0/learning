Manual Acknowledgement

Take personal control over when Kafka offsets get committed — useful for exactly-once-ish workflows, but easy to forget to call.

1. Why Manual Acknowledgement?

By default, Spring Cloud Stream's Kafka binder commits offsets on your behalf — typically after each record (or batch) is successfully processed. Most applications never need to think about this. Manual acknowledgement is the escape hatch: it lets your function say precisely when an offset is safe to commit, e.g. after a downstream database write or downstream publish has succeeded. This is the foundation of patterns like consume-transform-produce with at-least-once or exactly-once semantics.

2. The Switch: ackMode: MANUAL

This is a Kafka-binder-specific consumer property — it lives under the spring.cloud.stream.kafka.bindings.<target>.consumer namespace, not the portable bindings namespace from the core model:

spring:
  cloud:
    stream:
      kafka:
        bindings:
          process-in-0:
            consumer:
              ackMode: MANUAL
Other AckMode values (defined by Spring for Apache Kafka's ContainerProperties.AckMode enum): AUTO, AUTO_IMMEDIATE, MANUAL, MANUAL_IMMEDIATE, RECORD, BATCH. The binder's default is effectively BATCH (commit after the listener returns for each poll). Switching to MANUAL puts you in charge.
Two flavors of MANUAL:
• MANUAL — the ack you call is applied when the next poll() happens (deferred commit).
• MANUAL_IMMEDIATE — the ack commits the offset synchronously, right away.
Same acknowledge() call; the difference is timing.
Channel-name convention: The kafka.bindings key uses the input channel/binding name. In the functional model this is your bean name with its -in-0 / -out-0 suffix. The docs example uses the legacy literal input — translate it to your actual destination binding name.

3. Grabbing the Acknowledgment

Once ackMode is MANUAL, the binder attaches an Acknowledgment object to the message, available via the KafkaHeaders.ACKNOWLEDGMENT header. You must accept Message<?> (not just the payload) to reach it:

@SpringBootApplication
public class ManuallyAcknowledgingConsumer {

    @Bean
    public Consumer<Message<?>> process() {
        return message -> {
            Acknowledgment ack = message.getHeaders()
                .get(KafkaHeaders.ACKNOWLEDGMENT, Acknowledgment.class);
            if (ack != null) {
                System.out.println("Acknowledgment provided");
                ack.acknowledge();
            }
        };
    }
}

Key points:

  • Signature must be a Consumer<Message<?>> (or Message<T>) — a bare Consumer<T> has no headers, so no access to the Acknowledgment.
  • Always null-check — the header may be absent under some configurations or in tests.
  • Calling acknowledge() marks the offset (immediately or deferred, per your AckMode). The offset not committed is the next record to read.

4. What Happens If You Forget?

If ackMode is MANUAL and your listener returns without calling acknowledge(), the offset is not committed. On the next poll the consumer still sees the unacked records — effectively a redelivery loop. Always ensure your acknowledge call is reached on every path (including after errors, if that's the desired behavior), or pick AUTO / BATCH defaults instead.

5. nack(index, sleep) — Partial-Batch Rejection

In batch mode (Lesson 0025), Acknowledgment gives you more than acknowledge() — it provides nack(int index, long sleep). This commits offsets for all records before the given index, sleeps, then redelivers the remaining records of the batch. This is the recommended retry mechanism in batch mode since binder retry is disabled:

@Bean
public Consumer<Message<List<Widget>>> processBatch() {
    return message -> {
        List<Widget> batch = message.getPayload();
        Acknowledgment ack = message.getHeaders()
            .get(KafkaHeaders.ACKNOWLEDGMENT, Acknowledgment.class);
        try {
            for (int i = 0; i < batch.size(); i++) {
                handle(batch.get(i));
            }
            if (ack != null) ack.acknowledge();
        } catch (Exception e) {
            // commit the good prefix, redeliver the rest
            if (ack != null) ack.nack(failedIndex, 1000L);
        }
    };
}

6. When to Reach for Manual Ack

ScenarioUse manual ack?
Plain fire-and-forget consumerNo — default BATCH is fine
Consume → write to DB / call external APIYes — ack only after the side effect succeeds
Consume → produce on Kafka (consume-transform-produce)Yes — combine with a producer transaction for exactly-once
Batch consumer needing partial failure isolationYes — use nack(index, sleep)
