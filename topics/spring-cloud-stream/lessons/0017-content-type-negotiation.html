Content Type Negotiation

Let a producer and consumer agree on data meaning, not merely the bytes that crossed the broker.

1. The Broker Carries Bytes; Your Function Needs a Type

A binder typically exchanges a wire representation such as bytes. Your function is clearer when it receives a domain type:

@Bean
Consumer<InventoryEvent> inventoryConsumer() {
    return event -> reserveStock(event);
}

Content type negotiation chooses a MessageConverter that can transform the incoming payload into the function argument type. The content type is carried in a message header when available; a binding's content-type property supplies the contract when a producer does not provide usable metadata.

2. JSON Is the Default Contract

Spring Cloud Stream's default content type is application/json. Its JSON converter can turn a JSON payload into a POJO on input and turn a POJO into JSON on output. This makes a standard producer and consumer work without manual serialization code.

Content typeConverter intentUseful handler type
application/jsonJSON to/from objectA domain POJO or record
text/plainObject to/from textString
application/octet-streamPass bytes throughbyte[]
Contract first: use content-type to state the payload format, not to describe the Java class. The target handler type tells the converter what object to construct.

3. Set a Binding Contract When It Matters

A binding-level setting is useful when the producer is external, the expected format is not JSON, or you want the contract explicit in configuration. It is configured alongside the destination and group from Lesson 0016.

spring:
  cloud:
    function:
      definition: inventoryConsumer
    stream:
      bindings:
        inventoryConsumer-in-0:
          destination: inventory-events
          group: inventory-service
          content-type: application/json

A producer may set a message-level contentType header. That per-message metadata is more specific than a binding default, so use it only when one binding legitimately receives multiple documented formats.

4. Native Serialization Is a Different Path

When use-native-decoding is enabled on a consumer or use-native-encoding is enabled on a producer, the broker client library serializes or deserializes the payload. Spring Cloud Stream's content-type-based conversion is bypassed for that direction.

spring:
  cloud:
    stream:
      bindings:
        inventoryConsumer-in-0:
          consumer:
            use-native-decoding: true
Do not enable native conversion casually. It transfers responsibility for compatible serializers, deserializers, and payload format to the producer and consumer client configuration.

5. Extend Conversion Only for a Real New Format

The supplied converters cover JSON, text, and byte arrays. When an application genuinely owns another media type, register a MessageConverter bean that advertises that MIME type and supports the required target class. A custom converter is part of every producer-consumer compatibility contract.

Assessment

Retrieval Practice:

1. A broker delivers bytes, but your function accepts InventoryEvent. What component performs the transformation, and what two pieces of information guide it?

2. What is Spring Cloud Stream's default content type, and which handler payload type naturally fits it?

3. When would you configure inventoryConsumer-in-0.content-type, and when would a message-level contentType header be more specific?

4. What changes when use-native-decoding: true is enabled, and who becomes responsible for compatible serialization?

5. Name the supplied content types for JSON, text, and raw bytes. When is a custom MessageConverter justified?
