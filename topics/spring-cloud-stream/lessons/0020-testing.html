Testing with the Test Binder

Test your stream functions in-JVM — a real binder, no broker, no network.

1. A Real Binder Without the Network

Spring Cloud Stream ships a test binder based on the Spring Integration framework. It acts as an in-JVM message broker — giving you a real binder (full binding lifecycle, conversion, function invocation) without a real broker or any networking. It bridges unit and integration testing.

Why it matters: you can assert that your Function, Consumer, or Supplier behaves correctly through the actual Spring Cloud Stream machinery — not just calling the function directly. Binding names, content-type conversion, and routing are all exercised.

2. Setup

Add the test binder dependency (test scope only):

<!-- Maven -->
<dependency>
    <groupId>org.springframework.cloud</groupId>
    <artifactId>spring-cloud-stream-test-binder</artifactId>
    <scope>test</scope>
</dependency>
// Gradle (Kotlin DSL)
testImplementation("org.springframework.cloud:spring-cloud-stream-test-binder")

Then annotate your test configuration with @EnableTestBinder. This replaces any real binder on the classpath with the test binder for the test context.

3. The Two Test Harness Beans

The test binder exposes two beans you inject to drive messages in and assert messages out:

BeanRoleKey methods
InputDestinationSend messages into the function's input bindingsend(Message), send(Message, bindingName)
OutputDestinationReceive messages from the function's output bindingreceive(), receive(timeout, bindingName)

4. Simplest Test: One Function

@SpringBootTest
public class SampleStreamTests {

    @Autowired
    private InputDestination input;

    @Autowired
    private OutputDestination output;

    @Test
    public void testUppercase() {
        this.input.send(new GenericMessage<byte[]>("hello".getBytes()));
        assertThat(output.receive().getPayload()).isEqualTo("HELLO".getBytes());
    }

    @SpringBootApplication
    @EnableTestBinder
    public static class SampleConfiguration {
        @Bean
        public Function<String, String> uppercase() {
            return v -> v.toUpperCase();
        }
    }
}

Send "hello" in, assert "HELLO" comes out. The test binder handles the binding wiring, content-type conversion, and function invocation — exactly as a real binder would.

5. Multiple Functions & Explicit Binding Names

When you have multiple functions, pass the binding name to send() and receive() to target a specific function's input or output:

@Test
public void testMultipleFunctions() {
    try (ConfigurableApplicationContext context = new SpringApplicationBuilder(
            TestChannelBinderConfiguration.getCompleteConfiguration(
                    SampleFunctionConfiguration.class))
            .run("--spring.cloud.function.definition=uppercase;reverse")) {

        InputDestination inputDestination = context.getBean(InputDestination.class);
        OutputDestination outputDestination = context.getBean(OutputDestination.class);

        Message<byte[]> inputMessage = MessageBuilder.withPayload("Hello".getBytes()).build();
        inputDestination.send(inputMessage, "uppercase-in-0");
        inputDestination.send(inputMessage, "reverse-in-0");

        assertThat(outputDestination.receive(0, "uppercase-out-0").getPayload())
                .isEqualTo("HELLO".getBytes());
        assertThat(outputDestination.receive(0, "reverse-out-0").getPayload())
                .isEqualTo("olleH".getBytes());
    }
}
Use destination names when you map them. If you set spring.cloud.stream.bindings.uppercase-in-0.destination=myInput, then you must send to "myInput" — not the binding name. The test binder honors the same destination mapping as production.

6. Testing PollableMessageSource

The test binder also supports PollableMessageSource (polled consumers). It provides a default MessageSource that returns a fixed payload — sufficient for most tests. To supply your own data, register a MessageSource<?> bean:

@Bean
public MessageSource<?> source() {
    return () -> new GenericMessage<>("My Own Data " + UUID.randomUUID());
}
Do not name this bean messageSource. It conflicts with a Spring Boot bean of the same name (different type). Use any other name, e.g. source.

7. Two Ways to Build the Test Context

ApproachWhen to use
@SpringBootTest + @EnableTestBinder on a nested config classSingle configuration per test class — simplest, most common
TestChannelBinderConfiguration.getCompleteConfiguration(...) via SpringApplicationBuilderMultiple configurations in one test class, or fine-grained control over properties passed at runtime

Retrieval Practice:

1. What is the test binder, what framework does it build on, and what does it give you that a plain unit test calling a function directly does not?

2. Name the two beans the test binder injects for driving messages in and asserting messages out, and one key method on each.

3. In the multiple-function test, why do you pass "uppercase-in-0" to send() rather than just calling send(message)? What changes if you set a destination for that binding?

4. When testing a PollableMessageSource, what does the test binder provide by default, and how do you supply your own data? What bean name must you avoid and why?

5. Contrast the two ways to build the test context (@EnableTestBinder vs. TestChannelBinderConfiguration) — when would you choose each?
