Observability

See whether events are flowing, find a single event's path, and explain failures with evidence.

1. A Message Is Not Observable Just Because It Was Logged

Message-driven systems fail at a distance: a producer may be healthy while a consumer is slow, retrying, or unable to reach a dependency. Logs are useful evidence, but they are not enough to answer every operational question. Use three complementary signals.

SignalBest questionExample
MetricsIs this binding healthy over time?Rate, errors, latency, backlog or consumer lag.
TracesWhere did one event go?Producer send, broker handoff, consumer processing.
LogsWhat happened at this step?Business ID, exception, and recovery decision.
Operational habit: start from the question. A rising failure rate is a metrics question; a single missing order is a tracing question; the cause of a rejected event is a logging question.

2. Micrometer Is the Common Vocabulary

Spring Boot Actuator supplies the observability infrastructure, and Micrometer records observations so the same application can export metrics and traces to the systems your organization uses. Add Actuator before expecting useful operational endpoints or metric export.

<dependency>
  <groupId>org.springframework.boot</groupId>
  <artifactId>spring-boot-starter-actuator</artifactId>
</dependency>

<dependency>
  <groupId>io.micrometer</groupId>
  <artifactId>micrometer-tracing-bridge-brave</artifactId>
</dependency>

The tracing bridge is what lets observations participate in distributed traces. Select the bridge/exporter that matches your deployment rather than treating the example as mandatory for every application.

3. Follow One Event Across Boundaries

When tracing is configured, propagation metadata travels with the message so downstream work can join the same trace. That lets an operator move from a request that created an event to the consumer that processed it, rather than correlating timestamps manually.

Make logs trace-friendly: log a stable business identifier such as orderId, and let the logging configuration include trace and span identifiers. Do not log raw message bodies or secrets merely to make an event searchable.

4. Binder Capability Is Still Relevant

The observability model is shared, but a binder may require its own activation property. For example, the Kafka binder's observation registry is disabled by default:

spring:
  cloud:
    stream:
      kafka:
        binder:
          enable-observation: true

This is a useful boundary: use Actuator and Micrometer for the application-wide model, then consult the selected binder documentation for its transport-level signals and switches. Kafka-specific metrics and detailed broker lag analysis belong later in the Kafka Binder phase.

5. Diagnose the Right Layer

SymptomFirst signalNext action
Events arrive slowlyRate/latency metricCompare producer rate, consumer rate, and broker backlog.
One order disappearedTrace plus business IDFind the last producer/consumer span, then inspect its logs.
Failures rose after a releaseError metric plus logsIdentify the failing exception and check retry or DLQ outcomes.
