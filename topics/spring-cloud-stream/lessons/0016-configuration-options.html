Configuration Options

Make each message flow explicit without repeating every production policy on every binding.

1. A Binding Is the Unit You Configure

In the functional model, a function's input and output each have a binding name. For a consumer bean named inventoryConsumer, its input binding is inventoryConsumer-in-0. That name is the address used for its destination, consumer group, and per-binding policy.

@Bean
Consumer<InventoryEvent> inventoryConsumer() {
    return event -> process(event);
}
Practical rule: configure the binding name, not the Java method's internal implementation. The binding connects code to messaging infrastructure.

2. Separate the Message Contract From Behavior

Every binding needs a destination: the logical broker address. An input binding also commonly needs a group so multiple instances can share work and retain a stable consumer identity. Other settings control how that binding behaves, such as content type, concurrency, and retry.

spring:
  cloud:
    function:
      definition: inventoryConsumer
    stream:
      bindings:
        inventoryConsumer-in-0:
          destination: inventory-events
          group: inventory-service
          content-type: application/json
          consumer:
            concurrency: 2
            max-attempts: 5

This says where messages come from (destination), which cooperative consumer identity receives them (group), and how this consumer runs (consumer settings).

3. Put Shared Policy in Defaults

Repeated configuration is a source of drift. Set a safe shared baseline under spring.cloud.stream.default, then set a binding-level value only when it intentionally differs. A named binding overrides the relevant default.

spring:
  cloud:
    stream:
      default:
        content-type: application/json
        consumer:
          max-attempts: 3
          back-off-initial-interval: 1000
      bindings:
        paymentConsumer-in-0:
          consumer:
            max-attempts: 5

Here, every consumer gets three total attempts unless overridden; paymentConsumer-in-0 gets five. Defaults are a policy baseline, not a reason to hide important per-binding contracts such as destination and group.

4. Keep Binder-Specific Properties in Their Lane

Generic binding properties work through the binder abstraction. Transport-specific properties belong under that binder's namespace, for example spring.cloud.stream.kafka.bindings.<binding>.... This separation makes it clear which settings are portable and which tie the application to a broker.

Likewise, spring.cloud.stream.default-binder selects the binder used by default when more than one binder is available. Use a binding's binder property only when that particular binding must use a different configured binder.

Do not guess property names. The generic binding/property reference and the selected binder reference are both part of the configuration contract. Similar-looking broker properties can have very different semantics.

Configuration Review Drill

Assessment:

1. What is the input binding name for a functional consumer bean named inventoryConsumer, and why does that name matter?

2. In one sentence each, distinguish destination, group, and consumer.concurrency.

3. Where would you set a shared retry baseline of three total attempts, and where would you override only paymentConsumer-in-0 to five?

4. A team has Kafka and RabbitMQ binders on the classpath. What is the difference between default-binder and a binding's binder property?

5. Why should a Kafka-only configuration property not be placed under the generic spring.cloud.stream.bindings prefix?
