The Poller

How Spring Integration bridges the gap between pollable channels and message-driven endpoints.

Why this lesson exists

Non-blocking, message-driven processing works naturally with SubscribableChannel — the framework dispatches messages to handlers as they arrive. But PollableChannel (QueueChannel) introduces a problem: who pulls messages out of the queue and when?

The Poller is Spring Integration's answer. It's a scheduling component that periodically invokes a PollingConsumer endpoint, which checks a pollable channel for new messages and hands them to the message handler. Without a poller, a QueueChannel just accumulates messages in memory — nothing consumes them [ref].

Mission tie-in: The Poller is the bridge between the two message consumption models — subscribable (push) and pollable (pull). Understanding the poller unlocks QueueChannel, JdbcChannel, file adapters, and any source that produces messages on demand rather than on arrival.

1. The PollingConsumer

A PollingConsumer is an endpoint that polls an input channel rather than being subscribed to it. It wraps a message handler the same way an EventDrivenConsumer does — the difference is how it receives messages:

Endpoint typeTriggers whenUsed with
EventDrivenConsumerA message arrives on the channelSubscribableChannel (push)
PollingConsumerThe poller task firesPollableChannel (pull)

You can poll manually by calling PollableChannel.receive(timeout) directly in your code — a blocking call that returns the next message (or null on timeout). But the idiomatic approach is to let the framework handle it with a @Poller annotation.

// Manual polling (low-level)
QueueChannel channel = new QueueChannel(10);
channel.send(new GenericMessage<>("hello"));
Message<?> msg = channel.receive(1000); // blocks up to 1s

// Framework-driven polling (idiomatic)
@ServiceActivator(inputChannel = "queueChannel",
    poller = @Poller(fixedDelay = "500"))
public void handle(Message<?> msg) { ... }

2. Configuring the Poller with @Poller

The @Poller annotation configures the polling schedule on any endpoint that supports it (@ServiceActivator, @Transformer, @Splitter, etc.). Key attributes [ref]:

AttributeTypeDescription
fixedDelayString (ms)Delay after completion of the previous poll — the next poll starts this many ms after the last one finished.
fixedRateString (ms)Interval between start of polls — next poll starts regardless of whether the previous one finished.
cronStringUnix cron expression for time-of-day scheduling.
maxMessagesPerPollString (int)Max number of messages to receive per poll cycle. Default is unlimited (Long.MAX_VALUE).
receiveTimeoutString (ms)How long to wait for a message on receive() before the poll returns empty-handed.
taskExecutorStringBean name of a TaskExecutor for concurrent polling.
adviceChainString[]Bean names of Advice instances for cross-cutting concerns (retry, circuit breaker, conditional poll).
fixedDelay vs fixedRate: fixedDelay waits for the handler to finish before scheduling the next poll — ideal for rate-limited consumers. fixedRate fires on a fixed schedule regardless of handler duration — use when the schedule must be exact, even if polls overlap.

3. Pollable Message Source (MessageSource)

Not every source of messages is a channel. Some produce messages when you ask for them — files in a directory, rows in a database table, or state transitions. The MessageSource<T> interface wraps this pattern:

@FunctionalInterface
public interface MessageSource<T> {
    Message<T> receive();
}

A MessageSource is polled by a SourcePollingChannelAdapter — a special endpoint that does not need an input channel. Instead, it polls the source and forwards each received message to an output channel [ref].

@Bean
public IntegrationFlow sourceFlow() {
    return IntegrationFlow.from(() ->
        MessageBuilder.withPayload("item").build(),
        c -> c.poller(Pollers.fixedDelay(1000)))
        .handle(System.out::println)
        .get();
}

The contract: receive() returns a Message when available, or null when the source is exhausted. Returning null tells the framework to skip this poll cycle — the poller increments a counter of consecutive idle cycles (used by idle/active notifications). Once a source returns null, the framework will poll again on the next schedule.

4. Conditional Pollers & Smart Polling

Sometimes you need to skip a poll based on external state or optimize polling when the source is idle. Spring Integration provides several mechanisms [ref]:

  • PollSkipAdvice — A MethodInterceptor that wraps the poller's receive call. Its shouldSkip() method returns true to skip this poll cycle. Use for conditional polling (e.g., "don't poll on weekends").
  • ReceiveMessageAdvice — Extension point for receive() calls. The framework provides SimpleActiveIdleReceiveMessageAdvice (fires callbacks when the source transitions between active and idle states) and CompoundTriggerAdvice (allows an external trigger to fire a poll outside the normal schedule).
  • MessageSourceMutator — Transforms the MessageSource itself (sets headers, wraps payload, etc.) before each poll.
  • Trigger interface — Custom implementations of org.springframework.scheduling.Trigger for arbitrary scheduling logic.
// PollSkipAdvice — skip polls on weekends
public class WeekendSkipAdvice extends PollSkipAdvice {
    @Override
    public boolean shouldSkip(Message<?> message, Object... args) {
        return Calendar.getInstance().get(Calendar.DAY_OF_WEEK)
                in (Calendar.SATURDAY, Calendar.SUNDAY);
    }
}

// Attach to a poller:
@ServiceActivator(inputChannel = "in",
    poller = @Poller(fixedDelay = "1000", adviceChain = "weekendSkipAdvice"))

5. Deferred Acknowledgment

A QueueChannel with a poller removes a message from the queue when receive() is called — the message is gone even if the handler fails later. In transactional scenarios you may want to defer the acknowledgment until the handler confirms success [ref].

Spring Integration supports deferred acknowledgment via the transaction synchronization mechanism: the poller can participate in a transaction, and the message is acknowledged only after the transaction commits. If the transaction rolls back, the message is returned to the queue.

Key takeaways

  • The Poller is a scheduling component that drives PollingConsumer endpoints — it's what makes QueueChannel useful.
  • Two polling styles: manual (receive(timeout)) for ad-hoc consumption, framework-driven (@Poller) for idiomatic Spring Integration.
  • @Poller attributes: fixedDelay (delay after completion), fixedRate (interval between starts), cron, maxMessagesPerPoll, receiveTimeout, taskExecutor, adviceChain.
  • MessageSource is a pollable producer of messages — doesn't require an input channel. The SourcePollingChannelAdapter bridges it to the messaging flow.
  • Conditional polling via PollSkipAdvice, ReceiveMessageAdvice, and MessageSourceMutator adapts polling behaviour to external state.
  • When a MessageSource.receive() returns null, the framework records an idle cycle and polls again on the next schedule.

Test your understanding of the Poller.

What is the primary purpose of a PollingConsumer?

  • To transform message payloads
  • To poll a PollableChannel and hand messages to a handler
  • To subscribe to a PublishSubscribeChannel
  • To create new channels

A PollingConsumer wraps a message handler and uses a poller to periodically check a PollableChannel for messages.

What is the difference between fixedDelay and fixedRate in @Poller?

  • There is no difference
  • fixedDelay waits for the handler to complete before scheduling the next poll; fixedRate polls on a fixed schedule regardless of handler duration
  • fixedRate is faster than fixedDelay
  • fixedDelay is for cron-based scheduling

fixedDelay measures delay from completion of the previous poll. fixedRate measures from start — polls can overlap if the handler runs longer than the interval.

What does PollableChannel.receive(timeout) return when no message arrives within the timeout?

  • An error message
  • An empty Optional
  • null
  • false

receive(timeout) blocks until a message arrives or the timeout expires, returning null on timeout.

What does the maxMessagesPerPoll attribute control?

  • The maximum number of poller threads
  • How many messages the poller can retrieve in a single poll cycle
  • The maximum queue capacity
  • The maximum message size

maxMessagesPerPoll limits how many messages are received per poll. Default is unlimited (Long.MAX_VALUE). Setting it to 1 drains one message per poll cycle.

What does a MessageSource.receive() return when the source is exhausted?

  • An empty Optional
  • null
  • A message with an error payload
  • void

Returning null signals that no message is available this cycle. The framework records an idle cycle and polls again on schedule.

Which endpoint type bridges a MessageSource to the messaging flow?

  • EventDrivenConsumer
  • SourcePollingChannelAdapter
  • PollingConsumer
  • ChannelAdapter

SourcePollingChannelAdapter polls a MessageSource and forwards messages to an output channel. It needs no input channel.

What is PollSkipAdvice used for?

  • To skip processing when a message is null
  • To conditionally skip a poll cycle based on external state
  • To skip sending messages to error channels
  • To reduce logging verbosity

PollSkipAdvice wraps the poller's receive call. Its shouldSkip() method returns true to skip this poll cycle — e.g., "don't poll on weekends".

In deferred acknowledgment, when is the message acknowledged as consumed?

  • Immediately when receive() returns
  • After the transaction commits
  • When the handler logs completion
  • On the next poll cycle

Deferred acknowledgment uses transaction synchronization: the message is acknowledged only after the enclosing transaction commits. If the transaction rolls back, the message returns to the queue.

Which advice provides idle/active state transitions for a polled source?

  • PollSkipAdvice
  • SimpleActiveIdleReceiveMessageAdvice
  • CompoundTriggerAdvice
  • MessageSourceMutator

SimpleActiveIdleReceiveMessageAdvice fires callbacks when the source transitions between active (receiving messages) and idle (receiving null) states.
