Content Enricher

A message endpoint that adds data to a message by consulting an external source — filling in the gaps when a message carries only a partial payload.

Why this lesson exists

A Content Enricher is a Message Endpoint that augments an incoming message with additional data obtained from an external source (a database, REST service, or another flow). This is the Enterprise Integration Pattern for the common scenario where a message contains only a key or ID, and the full payload must be fetched before processing can continue [ref].

Spring Integration provides two enricher variants:

  • Header Enricher — adds or modifies message headers via static values or SpEL expressions.
  • Payload Enricher (ContentEnricher) — enriches the message payload by sending a request to a downstream service and merging the response back into the original payload.
Key distinction: The Header Enricher adds headers to the existing message. The Payload Enricher replaces specific properties on the existing payload object using values from a reply message. The original payload stays as the root object for property mappings.

1. Header Enricher — Java configuration

The HeaderEnricher class accepts a Map<String, HeaderValueMessageProcessor<?>> where each entry defines a header name and its value processor [ref]:

Map<String, HeaderValueMessageProcessor<?>> headers = new HashMap<>();
headers.put("source", new StaticHeaderValueMessageProcessor<>("enricher-java"));
headers.put("length",
        new ExpressionEvaluatingHeaderValueMessageProcessor<>(
                "payload.length()", Integer.class));

HeaderEnricher enricher = new HeaderEnricher(headers);
enricher.setDefaultOverwrite(false);  // don't overwrite existing headers

The setDefaultOverwrite(false) flag means existing headers with the same name are preserved — the enricher only adds missing headers. You can override per-header with specific HeaderValueMessageProcessor instances that have their own overwrite flag.

2. Header Enricher — DSL

The DSL provides a concise .enrichHeaders() step that accepts a Consumer<HeaderEnricherSpec> [ref]:

@Bean
public IntegrationFlow headerDslFlow() {
    return IntegrationFlow.from("in")
            .enrichHeaders(h -> h
                    .header("dslSource", "enricher-dsl")
                    .headerExpression("upperCase", "payload.toUpperCase()")
            )
            .channel("out")
            .get();
}

The header() method sets a static literal value, while headerExpression() evaluates a SpEL expression against the message.

3. Payload Enricher with request channel

The Payload Enricher (ContentEnricher) is configured via the DSL's .enrich() step [ref]:

@Bean
public IntegrationFlow enricherFlow() {
    return IntegrationFlow.from("in")
            .enrich(e -> e
                    .requestChannel("lookupRequest")
                    .requestPayload(p -> ((Ticket) p.getPayload()).getId())
                    .propertyExpression("assignee", "payload.assignee")
                    .propertyExpression("status", "payload.status")
            )
            .channel("out")
            .get();
}

The enricher works in three phases:

  1. Extract — requestPayload() derives the request message payload from the original message (e.g., extracting the ticket ID).
  2. Fetch — The request is sent to requestChannel, which invokes a downstream service that returns a reply.
  3. Merge — propertyExpression() maps values from the reply (accessed via payload.*) onto the original payload object using JavaBean property setters.

The original payload object must have JavaBean setters for each property being enriched. Records (Java record) don't work because their fields are final — use a regular POJO with setters instead.

4. Static payload enrichment (no request channel)

If you omit requestChannel, the enricher fills properties from SpEL expressions without making an external call. This is useful for setting default values:

@Bean
public IntegrationFlow staticEnrichFlow() {
    return IntegrationFlow.from("in")
            .enrich(e -> e
                    .propertyExpression("assignee", "'system'")
                    .property("status", "pending")
            )
            .channel("out")
            .get();
}

property() sets a literal value, and propertyExpression() evaluates a SpEL expression. The expression context is the reply message — but with no request channel, the expression is evaluated against a null reply, so you typically use literal strings or context beans.

Key takeaways

  • Header Enricher adds headers via static values (header()) or SpEL (headerExpression()).
  • Payload Enricher (ContentEnricher) fetches data from a request channel and merges it onto the original payload object.
  • .enrichHeaders() is the DSL method for header enrichment; .enrich() is for payload enrichment.
  • The enriched payload object must have JavaBean setters for each property — Java records won't work.
  • setDefaultOverwrite(false) preserves existing headers when using HeaderEnricher directly.
  • The requestPayload() function extracts data from the original message to form the request to the lookup service.

Action / Assessment

Test your understanding of the Content Enricher.

What is the primary purpose of a Content Enricher endpoint?

  • To transform message payload from one type to another
  • To augment a message with additional data obtained from an external source
  • To filter messages based on content
  • To route messages to different channels

The Content Enricher fills in missing data by consulting a database, service, or another flow, then merges the result back onto the original payload.

What does the setDefaultOverwrite(false) flag on HeaderEnricher do?

  • Prevents any headers from being added
  • Preserves existing headers — only adds missing ones
  • Clears all existing headers before enrichment
  • Throws an exception if headers already exist

When false, existing headers with the same name are not overwritten. The enricher only adds headers that don't already exist on the message.

Which DSL method is used for payload enrichment?

  • .enrichHeaders()
  • .enrich()
  • .transform()
  • .handle()

.enrich() accepts a Consumer<EnricherSpec> for configuring the ContentEnricher. .enrichHeaders() is specifically for header enrichment.

Why must the enriched payload object have JavaBean setters?

  • Because the enricher uses reflection to read fields
  • Because the enricher uses property setters to merge values back onto the original payload
  • Because the enricher serializes the payload to XML
  • Because setters are required for SpEL evaluation

The ContentEnricher maps reply values onto the original payload via JavaBean setter methods. A Java record's fields are final, so records cannot be used as enriched payloads.

What happens if you omit requestChannel in .enrich()?

  • The enricher throws a configuration error
  • The enricher sends the request to a default channel
  • The enricher fills properties from SpEL expressions without making an external call
  • The enricher creates a temporary channel automatically

Without a request channel, there's no external lookup. Properties are set from literal values or SpEL expressions, which is useful for assigning default values.

Which method derives the request payload from the original message in EnricherSpec?

  • .requestPayload(String)
  • .requestPayload(Function<Message<P>, ?>)
  • .requestPayloadExpression(String)
  • Both B and C are valid

requestPayload() accepts a Function to extract data from the original message. requestPayloadExpression() does the same via SpEL. Both are valid.

What is the difference between .header() and .headerExpression() on HeaderEnricherSpec?

  • They are identical
  • .header() sets a static literal; .headerExpression() evaluates a SpEL expression
  • .header() sets the reply channel; .headerExpression() sets the request channel
  • .header() is for strings only; .headerExpression() is for numbers

.header(key, value) sets a literal value directly. .headerExpression(key, expr) evaluates a SpEL expression against the message context to compute the value dynamically.
