Channel Interceptors

Intercepting send and receive operations with ChannelInterceptor, global interceptors, and the wire tap pattern.

Why this lesson exists

By now you know that every message crosses a channel between producer and consumer. But what if you need to inspect, modify, or redirect a message at the moment it passes the channel boundary — without changing the producer or consumer code?

That is exactly what ChannelInterceptor gives you: hook methods that fire before and after every send() and receive() call. You can validate messages, measure latency, redact sensitive headers, or copy messages to a monitoring channel — all through a single strategy interface [ref].

Mission tie-in: Every production integration needs cross-cutting observability — message logging, audit trails, SLA monitoring. Channel interceptors are where you add that without polluting your business endpoints. The wire tap pattern (a specialised interceptor) is the standard way to feed messages to a logging or metrics pipeline without slowing the main flow.

The ChannelInterceptor interface

Six hook methods, three for send and three for receive [ref]:

public interface ChannelInterceptor {

    Message<?> preSend(Message<?> message, MessageChannel channel);

    void postSend(Message<?> message, MessageChannel channel, boolean sent);

    void afterSendCompletion(
            Message<?> message, MessageChannel channel, boolean sent, Exception ex);

    boolean preReceive(MessageChannel channel);

    Message<?> postReceive(Message<?> message, MessageChannel channel);

    void afterReceiveCompletion(
            Message<?> message, MessageChannel channel, Exception ex);
}

Send lifecycle

MethodWhen it firesWhat you can do
preSendAfter a producer calls send(), before the message is dispatched to subscribersModify the message, return null to veto delivery
postSendImmediately after the message has been dispatchedObserve success (sent=true) or rejection (sent=false but no exception). Not called when preSend returns null.
afterSendCompletionAfter the entire send operation completes (success or exception)Cleanup — fires after the message is dispatched (or when an exception occurs). Not called when preSend returns null.

Receive lifecycle

MethodWhen it firesWhat you can do
preReceiveAfter a consumer calls receive(), before the message is retrieved from a buffered channelReturn false to veto the receive
postReceiveImmediately after a message has been receivedModify the message before the consumer sees it
afterReceiveCompletionAfter the receive operation completesCleanup — always fires
preSend returns a Message — not void. To modify the message, return a new or transformed copy. To veto delivery entirely, return null — the framework treats a null return as "cancel this send".

Attaching an interceptor to a channel

Interceptors are registered on the channel's interceptors list. In Java configuration [ref]:

@Bean
public DirectChannel myChannel() {
    DirectChannel channel = new DirectChannel();
    channel.addInterceptor(myInterceptor());
    return channel;
}

@Bean
public MyInterceptor myInterceptor() {
    return new MyInterceptor();
}

Or inline with a lambda:

channel.addInterceptor(new ChannelInterceptor() {
    @Override
    public Message<?> preSend(Message<?> message, MessageChannel channel) {
        log.info("Sending: {}", message.getPayload());
        return message;
    }
});

Global interceptors (@GlobalChannelInterceptor)

Attaching interceptors one channel at a time gets repetitive. Spring Integration provides @GlobalChannelInterceptor — a bean-level annotation that applies your interceptor to all channels (or a named subset) [ref]:

@Bean
@GlobalChannelInterceptor(patterns = "input*", order = 3)
public ChannelInterceptor loggingInterceptor() {
    return new ChannelInterceptor() {
        @Override
        public Message<?> preSend(Message<?> message, MessageChannel channel) {
            log.info("[{}] sending: {}", channel, message.getPayload());
            return message;
        }
    };
}
AttributeMeaningDefault
patternsComma-separated glob patterns (e.g. "input*, !cat*" to exclude cat*)"*" — all channels
orderControls execution order relative to other global interceptorsLast (lowest precedence)

If multiple global interceptors match, they run in order ascending. Interceptors registered directly on a specific channel run after global interceptors by default (but this can be configured with setInterceptorCaptureMaxCount and ordering on the channel dispatcher).

The wire tap pattern

A wire tap is a non-intrusive interceptor that copies every message to a secondary channel — for logging, auditing, metrics, or debugging — without affecting the primary message flow [ref].

Spring Integration provides the WireTap class, which implements ChannelInterceptor. You add it to a channel the same way:

@Bean
public DirectChannel orders() {
    return new DirectChannel();
}

@Bean
@GlobalChannelInterceptor(patterns = "orders")
public WireTap ordersWireTap(MessageChannel auditChannel) {
    return new WireTap(auditChannel);
}

@Bean
public DirectChannel auditChannel() {
    return new DirectChannel();
}

Every message sent to the orders channel is also sent (as a copy) to auditChannel. The primary subscriber on orders is unaffected.

You can also configure a wire tap inline on a channel built via the Java DSL [ref]:

@Bean
public PollableChannel myChannel() {
    return MessageChannels.queue()
            .wireTap("loggingFlow.input")
            .get();
}
When to wire tap: use a wire tap for cross-cutting concerns (logging, metrics, audit). Use a custom ChannelInterceptor when you need to modify or veto messages — the wire tap is deliberately read-only.

Practical: vetoing messages

Returning null from preSend cancels the send. This is useful for traffic filtering, rate limiting, or content-based gating:

channel.addInterceptor(new ChannelInterceptor() {
    @Override
    public Message<?> preSend(Message<?> message, MessageChannel channel) {
        if ("DROP".equals(message.getPayload())) {
            log.warn("Vetoed: {}", message.getPayload());
            return null;     // ← cancels this send
        }
        return message;
    }
});

When a message is vetoed, send() returns false. Neither postSend nor afterSendCompletion fires — the send is aborted before dispatch.

Interceptors vs subscribers: the order

Understanding the execution order is critical for debugging:

  1. Global interceptors (@GlobalChannelInterceptor) run in order ascending.
  2. Channel-specific interceptors (channel.addInterceptor()) run next.
  3. The message is dispatched to subscriber(s).
  4. postSend fires with the result (only if the message was not vetoed).
  5. afterSendCompletion fires for cleanup (only if the message was not vetoed).

On preReceive, the same layered order applies: global first, then channel-specific.

Three for the send lifecycle (preSend, postSend, afterSendCompletion) and three for receive (preReceive, postReceive, afterReceiveCompletion).

WireTap is a read-only interceptor that sends a copy of each message to another channel.

In what order do interceptors execute?

  • Alphabetical by bean name
  • Channel-specific, then global (by order)
  • Global interceptors (by order), then channel-specific interceptors
  • Declaration order on the channel

Global interceptors run first (sorted by order attribute), then channel-specific interceptors added via addInterceptor().

When postSend fires with sent=false, what does that mean?

  • The message was dispatched but could not be delivered within the timeout
  • An exception was thrown during dispatch
  • The channel has no subscribers registered
  • The channel is a PollableChannel

postSend only fires after dispatch — sent=false means the dispatcher found no accepting subscriber within the timeout. (A veto from preSend aborts before dispatch, so postSend is never called.)

What does preReceive return to veto a receive operation?

  • void — you cannot veto a receive
  • an empty Message
  • false
  • null

preReceive returns a boolean. Return false to cancel the receive before any message is retrieved.
