Configuring Message Channels

Datatype channels, dispatcher failover, executor channels, publish-subscribe sequencing, and bounded queues — the channel configuration options that tune flow behaviour.

Why this lesson exists

So far you've been creating channels with their default settings (new DirectChannel(), new QueueChannel()). But channels have important configuration levers you need to know about for production flows [ref]:

  • Datatype channels — restrict which payload types a channel accepts, with optional auto-conversion.
  • Dispatcher failover — control whether a channel tries the next handler when one throws.
  • Executor channels — hand off dispatch to a thread pool (different from the default caller-thread model).
  • Publish-subscribe sequencing — broadcast with sequenceSize / sequenceNumber headers for downstream aggregation.
  • Bounded queues — limit QueueChannel capacity to prevent memory exhaustion.
Mission tie-in: Choosing the right channel configuration is a core design skill. Datatype channels protect consumers from unexpected payloads. Failover control decides your flow's resilience strategy. Executor channels enable async hand-off. Sequence headers on broadcast channels feed aggregators. Bounded queues prevent back-pressure from turning into OOM errors.

1. Datatype Channel

A Datatype Channel restricts the payload types accepted by a channel [ref]. If the payload doesn't match, the channel either:

  • Throws MessageDeliveryException if no conversion is possible, or
  • Converts it via the integrationConversionService if a matching Converter is registered.
@Bean
public MessageChannel numberChannel() {
    DirectChannel channel = new DirectChannel();
    channel.setDatatypes(Number.class);
    return channel;
}

You can provide multiple types and register converters with @IntegrationConverter:

@Bean
public MessageChannel numberChannel() {
    DirectChannel channel = new DirectChannel();
    channel.setDatatypes(String.class, Number.class);
    return channel;
}

@Bean
@IntegrationConverter
public StringToIntegerConverter strToInt() {
    return new StringToIntegerConverter();
}

The type check uses isAssignableFrom — so Integer and Double both satisfy Number.class.

2. Dispatcher Failover

DirectChannel (and ExecutorChannel) use a UnicastingDispatcher under the hood. By default, failover is enabled: if the first subscribed handler throws an exception, the dispatcher tries the next handler [ref].

When failover is disabled, the exception propagates immediately to the sender — no fallback handler is tried:

@Bean
public MessageChannel failFastChannel() {
    DirectChannel channel = new DirectChannel();
    channel.setFailover(false);
    return channel;
}

You can also pass null as the LoadBalancingStrategy to disable load-balancing entirely, creating a fixed-order dispatch:

@Bean
public MessageChannel fixedOrderChannel() {
    return new DirectChannel(null);   // no load-balancer, no failover
}

Since 6.3, you can also provide a Predicate<Exception> failoverStrategy for finer-grained decisions.

3. ExecutorChannel

An ExecutorChannel is point-to-point like DirectChannel, but the handler is invoked on a thread from the provided TaskExecutor pool, not the sender's thread [ref]. This breaks the single-threaded execution context — the send() call returns immediately, and the handler runs later on a pool thread.

@Bean
public MessageChannel executorChannel() {
    return new ExecutorChannel(someExecutor());
}
Important: Because the sender returns before the handler runs, any active transaction context is not propagated. The handler also can't send an exception back to the sender — errors go to the error channel instead.

4. PublishSubscribeChannel with applySequence

When you set applySequence = true on a PublishSubscribeChannel, the channel automatically adds sequenceSize and sequenceNumber headers to each copy [ref]. With 2 subscribers, the first gets sequenceNumber=1, sequenceSize=2 and the second gets sequenceNumber=2, sequenceSize=2. This is essential for downstream aggregators and resequencers (Phase 4 topics).

@Bean
public MessageChannel pubsubChannel() {
    PublishSubscribeChannel channel = new PublishSubscribeChannel();
    channel.setApplySequence(true);
    return channel;
}

Without this flag, each subscriber receives the same Message instance (payload and header references are shared; Spring Integration enforces immutability). With the flag, new Message instances are created with distinct sequence headers.

5. Bounded QueueChannel

A QueueChannel without a capacity is unbounded — it can grow until memory runs out [ref]. Always set a capacity:

@Bean
public PollableChannel boundedQueueChannel() {
    return new QueueChannel(25);
}

When the queue is full, send() blocks until space is available (or the send timeout expires). For persistent queues, you can provide a message-store attribute backed by JDBC, Redis, or MongoDB — this survives system restarts.

Key takeaways

  • Datatype channels enforce payload types at the channel boundary. Register @IntegrationConverter beans for auto-conversion.
  • Failover (default: on) lets the dispatcher try the next handler on exception. Disable it for fail-fast semantics.
  • ExecutorChannel breaks the caller's thread — the send() returns before the handler runs. No transaction propagation.
  • applySequence on PublishSubscribeChannel is required upstream of aggregators/resequencers.
  • Always bound your QueueChannel capacity — unbounded queues risk OOM under back-pressure.

Transaction context is thread-bound. Since the handler runs on a different thread, the sender's transaction is not visible to it.

Sequence headers allow an aggregator or resequencer to correlate and reorder the split copies back into a single result.
