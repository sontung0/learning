Overview: Messages, Channels & Endpoints

The three nouns every Spring Integration flow is built from — and why the framework lives inside your app instead of a separate server.

The one idea to hold onto

Spring Integration is Spring's implementation of the Enterprise Integration Patterns (EIP). It brings message-driven, pipes-and-filters design into an ordinary Spring ApplicationContext. Instead of your business code calling the next system directly, components hand messages to each other through channels, and your POJOs are wired in by endpoints. The framework handles routing, transformation, and scheduling; your code stays focused on the domain. [ref]

Mission tie-in: Your goal is to design production integrations independently. Every pattern you will learn later — routers, splitters, aggregators, adapters — is just a special kind of endpoint reading from and writing to channels, moving messages. Nail these three nouns now and the whole reference falls into place.

Application-centric, not a central ESB

A traditional Enterprise Service Bus (Mule, TIBCO, BizTalk) is a heavy, centralized runtime: applications connect as spokes to a hub you must patch, scale, and babysit. That hub is an operational bottleneck and a single point of failure.

Spring Integration takes the opposite stance — application-centric and embedded:

  • No dedicated integration server. Channels, endpoints, and transformers are just Spring beans living in your app's context.
  • Decentralized. Integration logic scales alongside your app instances, monolith or microservice.
  • POJO-based & testable. Because "everything is just Spring beans," flows unit-test with ordinary Spring test tooling — no middleware container to spin up.

[ref: Architectural Positioning]

The three main components

ComponentPipes-and-filters roleWhat it is
Message The thing that flows A generic wrapper: a payload (any Java object) plus headers (id, timestamp, correlationId, return address, and any key/value you add).
Message Channel The "pipe" Decouples producer from consumer. Can be point-to-point (one consumer per message) or publish-subscribe (all subscribers). Can be subscribable (message-driven) or pollable (buffers in a queue; needs a poller).
Message Endpoint The "filter" Connects your application code to the messaging system non-invasively — like an MVC controller for messages. Your POJO stays unaware of Message and MessageChannel.

Endpoints come in the flavours you'll spend the coming lessons on: transformer, filter, router, splitter, aggregator, service activator, and channel adapter (inbound/outbound, connecting the flow to an external system or transport). [ref: Message Endpoints]

Terminology trap: the pipes-and-filters "filter" means any endpoint (a filter is a component connected to a channel). The EIP Message Filter is the specific endpoint that decides whether a message passes at all. Same word, two meanings.

Wiring it up: @EnableIntegration and POJO methods

With pure Java config (i.e. Spring Boot), you must register the framework's infrastructure beans with @EnableIntegration. It installs the built-in errorChannel, the taskScheduler pollers use, annotation processors, and more. [ref: @EnableIntegration]

Spring Boot's spring-boot-starter-integration applies @EnableIntegration for you via auto-configuration — which is why the sandbox below just works.

You then write plain methods. The framework extracts the payload, invokes your method, and wraps the return value back into a message for the next component (copying the original headers):

@ServiceActivator(inputChannel = "greetings")
public String myService(String payload) {
    return "Hello, " + payload;
}

You can pull headers in too, without touching the Message type:

@ServiceActivator(inputChannel = "greetings")
public String myService(@Payload String payload, @Header("locale") String locale) {
    return greet(payload, locale);
}

Code along (sandbox)

Your first runnable flow: a QueueChannel (a pollable channel), a @ServiceActivator POJO subscribed to it via a poller, and a CommandLineRunner that sends one message in. Watch the log line the service activator produces.

The code lives in sandbox/src/main/java/com/learning/si/lesson0001/, guarded by the lesson0001 profile. Run it:

cd topics/spring-integration/sandbox
./mvnw spring-boot:run -Dspring-boot.run.profiles=lesson0001

You should see the message arrive, get handled by your POJO, and the greeting logged — a message flowing through a channel into an endpoint. That is the entire framework in miniature.

  • Application-centric beans embedded in the app context

A pollable channel differs from a subscribable channel because it ____.

  • buffers messages and needs a poller
  • always broadcasts to every consumer
  • cannot ever store a payload

Pollable channels queue messages (throttling the consumer); a consumer reads them only via a configured poller.

It wraps the return value into a reply message (copying original headers) and sends it to the output/return channel.
