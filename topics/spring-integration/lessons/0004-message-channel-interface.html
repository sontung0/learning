The MessageChannel Interface

The three core contracts that every channel implements — send, subscribe, and receive — and why the distinction matters at runtime.

Why this lesson exists

Lesson 0003 showed you what channels do (point-to-point vs publish-subscribe as a delivery mode). This lesson shows you the Java interface hierarchy behind those behaviours. Every channel you will ever declare — DirectChannel, QueueChannel, PublishSubscribeChannel, ExecutorChannel, PriorityChannel, FluxMessageChannel — implements one of two sub-interfaces of MessageChannel. Understanding this split tells you instantly whether a channel is push-based or pull-based without reading a one-liner.

Mission tie-in: When you design a production integration, choosing the wrong consumption model (push vs pull) is a common source of thread-pool exhaustion, dropped messages, or mysterious back-pressure bugs. Knowing the interface hierarchy means you diagnose the problem from the type, not from trial-and-error.

The interface hierarchy

Three interfaces, one root, two branches — [ref]:

MessageChannel                   // send(Message), send(Message, long)
  ├── SubscribableChannel        // subscribe(MessageHandler), unsubscribe(MessageHandler)
  │     └── DirectChannel, PublishSubscribeChannel, ExecutorChannel, FluxMessageChannel
  └── PollableChannel            // receive(), receive(long)
        └── QueueChannel, PriorityChannel, RendezvousChannel

1. MessageChannel — the root

Every channel in Spring Integration implements MessageChannel. It defines exactly two methods [ref]:

public interface MessageChannel {

    boolean send(Message message);

    boolean send(Message message, long timeout);
}
  • send(Message) delegates to send(message, -1) — block indefinitely.
  • send(Message, long) blocks up to timeout milliseconds, then returns false (not an exception) if delivery failed.
  • The boolean return value is the only signal of success or failure from the send side — no exceptions are thrown under normal rejection.

The second argument's meaning varies by implementation:

Channel typetimeout controls…
DirectChannelHow long to wait for a subscriber to accept the message (rarely a factor; dispatch is synchronous on the caller's thread).
QueueChannelHow long to wait for space in the bounded queue (if capacity is set).

2. SubscribableChannel — push-based

Extends MessageChannel for channels that maintain a registry of MessageHandler subscribers and dispatch to them directly [ref]:

public interface SubscribableChannel extends MessageChannel {

    boolean subscribe(MessageHandler handler);

    boolean unsubscribe(MessageHandler handler);
}
  • A handler is registered via subscribe() and removed via unsubscribe().
  • When send() is called, the channel iterates its subscribers and invokes handleMessage() on each (or one, depending on the implementation's dispatch behaviour).
  • This is a push model: the sender's thread does the work, or hands off to an executor (e.g., ExecutorChannel).
  • Implementations: DirectChannel (point-to-point, single subscriber), PublishSubscribeChannel (broadcast), ExecutorChannel (async via TaskExecutor), FluxMessageChannel (reactive).

The framework's EventDrivenConsumer endpoint calls subscribe() under the hood when you declare a @ServiceActivator(inputChannel = "…") on a SubscribableChannel. You do not normally call subscribe() yourself — but knowing it exists tells you how the wiring actually works.

3. PollableChannel — pull-based

Extends MessageChannel for channels that buffer messages and let a consumer pull them on demand [ref]:

public interface PollableChannel extends MessageChannel {

    Message<?> receive();

    Message<?> receive(long timeout);
}
  • receive() delegates to receive(-1) — block until a message arrives.
  • receive(long) blocks up to timeout milliseconds, then returns null if no message arrived.
  • This is a pull model: the consumer controls when to ask for the next message.
  • Implementations: QueueChannel (bounded / unbounded BlockingQueue), PriorityChannel (ordered by priority header), RendezvousChannel (direct hand-off, blocks both sides until the exchange completes).

The framework's PollingConsumer endpoint does the pulling — driven by a PollerMetadata (the @Scheduled-like poller you configured in Lesson 0001).

Why two branches?

The push/pull split maps directly to two integration realities:

SubscribableChannel (push)PollableChannel (pull)
ThreadingSender's thread invokes the handler (or an executor you supply).A scheduler thread calls receive() and hands off to the handler.
BufferingNo buffer — message must be accepted immediately or rejected.Messages sit in a queue until the consumer pulls them.
Back-pressureSender blocks if the subscriber is slow (same thread).Producer outruns consumer → queue grows (bounded or unbounded).
Transaction scopeSingle thread on both sides — declarative transactions "just work" across the channel.Transaction ends at the poller; the handler runs in a separate transaction.
Typical useIn-process flows where you want synchronous, single-threaded processing.Work queues, buffered entry points, rate-limited consumers.
Watch out for the QueueChannel + poller default: a QueueChannel is a PollableChannel, but declaring one without a poller means nobody ever calls receive() — messages sit in the queue forever. Lesson 0001's PollerMetadata.DEFAULT_POLLER bean is what made that flow work.

What this means for your sandbox code

In Lesson 0001 you declared a QueueChannel (a PollableChannel) with a default poller and a @ServiceActivator. The @ServiceActivator normally expects a SubscribableChannel (push), but the framework detects a PollableChannel and wraps the endpoint in a PollingConsumer — bridging the push annotation with a pull channel. That bridge only works because the default poller bean exists.

In this lesson's sandbox, you'll call subscribe() and receive() directly — no annotations, no poller — so you can feel the difference between push and pull in your fingers.

  • PollableChannel

DirectChannel implements SubscribableChannel — handlers are subscribed and invoked on the sender's thread.

  • PollableChannel
  • SubscribableChannel

QueueChannel implements PollableChannel — messages are buffered in a BlockingQueue and pulled via receive().

What does receive(0) return when a QueueChannel is empty?

  • null immediately
  • throws an EmptyQueueException
  • blocks forever
  • returns an empty Message with null payload

receive(0) returns null immediately — zero timeout means "do not wait".

What happens if you declare a @ServiceActivator on a QueueChannel without a poller?

  • The handler never fires — no one calls receive()
  • It works fine — QueueChannel is also subscribable
  • Spring Boot throws a configuration error at startup
  • The poller defaults to a fixedDelay of 1 millisecond

QueueChannel is PollableChannel-only. Without a PollerMetadata, no PollingConsumer is created, so receive() is never called.

Which channel type allows a single thread to operate on both sides of the channel, making declarative transactions work seamlessly?

  • DirectChannel (SubscribableChannel)
  • QueueChannel (PollableChannel)
  • PriorityChannel
  • RendezvousChannel

DirectChannel invokes the handler on the sender's thread — same thread, same transaction.

What does the boolean return value of send() indicate?

  • Whether delivery succeeded within the timeout
  • Whether the message was valid
  • Whether the channel has any subscribers
  • Whether the message was persisted

send() returns false if delivery failed within the timeout — it does not throw under normal rejection.

The framework's EventDrivenConsumer calls ____ on a SubscribableChannel to register its handler.

  • send(Message)
  • receive()

EventDrivenConsumer calls subscribe() with the endpoint's MessageHandler; the PollingConsumer equivalent uses a poller + receive().
