MessagingTemplate

Programmatic send, receive, and request-reply against channels — no endpoint annotations required.

Why this lesson exists

So far every lesson has wired channels and endpoints through declarative configuration: @ServiceActivator, @Bean channels, .subscribe() calls. But what if you need to send a message from application code — say, inside a controller, a scheduled task, or a test — without annotating a method?

That's what MessagingTemplate is for [ref]. It gives you a simple, imperative API:

  • send(channel, message) — fire-and-forget.
  • receive(channel) — pull the next message off a pollable channel.
  • sendAndReceive(channel, request) — send a request and block for a reply.
Mission tie-in: Not every integration flow is a pure pipes-and-filters pipeline. Sometimes you need to reach into the messaging system from business logic — send a command, poll a queue, or call a request-reply gateway. MessagingTemplate is the tool for that. It's also the imperative counterpart to the declarative @MessagingGateway you'll meet in Phase 6.

Core methods

MethodAcceptsReturnsUse case
send(MessageChannel, Message) Any channel boolean Fire-and-forget. Returns false on timeout.
receive(PollableChannel) Pollable channel Message<?> or null Pull next message; null means empty queue or timeout.
sendAndReceive(MessageChannel, Message) Any channel Message<?> Request-reply. Creates a temporary anonymous reply channel.

Timeouts control blocking behaviour:

  • setSendTimeout(long) — max ms to wait for the send to complete. Default: -1 (block forever).
  • setReceiveTimeout(long) — max ms to wait for receive(). Default: -1 (block forever).

How sendAndReceive works

When you call sendAndReceive, the template:

  1. Creates a temporary anonymous PollableChannel.
  2. Sets it as the outgoing message's replyChannel header.
  3. Sends the message to the target channel.
  4. Blocks on receive() against the temporary channel until the reply arrives.

The endpoint handling the request extracts the replyChannel header from the incoming message and sends its reply there. The template picks it up and returns it. This is the same return address pattern from EIP, orchestrated automatically.

Note: MessagingTemplate lives in org.springframework.integration.support — it's part of spring-integration-core, so no extra dependency.

Run the sandbox

cd topics/spring-integration/sandbox
./mvnw spring-boot:run -Dspring-boot.run.profiles=lesson0007

The runner demonstrates all three operations in sequence:

Section 1 — send()

A fire-and-forget send to a DirectChannel. The template returns immediately — the handler runs on the caller's thread.

Section 2 — receive()

Three messages are pre-loaded into a QueueChannel, then the template pulls them one at a time. The fourth call returns null because the queue is empty (and our receiveTimeout expires).

Section 3 — sendAndReceive()

A message is sent to a handler that uppercases the payload and sends it back via the replyChannel header. The template blocks until the reply arrives and returns it.

Heads up: Because sendAndReceive blocks the caller until a reply arrives, it's best used where the round-trip latency is predictable. For asynchronous request-reply, you'd use a @MessagingGateway with a CompletableFuture<?> return type — but that's a Phase 6 topic.

Key takeaways

  • MessagingTemplate is the imperative way to interact with channels from application code.
  • Three operations: send (fire-and-forget), receive (pull), sendAndReceive (request-reply).
  • sendAndReceive uses a temporary anonymous reply channel — the return address EIP.
  • Timeouts (sendTimeout, receiveTimeout) prevent indefinite blocking; -1 means block forever.
  • It's the imperative counterpart to @MessagingGateway (declarative request-reply).

What package does MessagingTemplate live in?

  • org.springframework.messaging.support
  • org.springframework.integration.support
  • org.springframework.integration.core
  • org.springframework.messaging.core

MessagingTemplate is in org.springframework.integration.support (spring-integration-core).

Which MessagingTemplate method creates a temporary anonymous reply channel?

  • send(channel, message)
  • receive(channel)
  • sendAndReceive(channel, request)
  • convertAndSend(channel, payload)

sendAndReceive creates a temporary PollableChannel, sets it as the replyChannel header, sends the message, and blocks for the reply.

What does MessagingTemplate.send() return when the message is delivered successfully?

  • The reply Message
  • true
  • void — it doesn't return a value
  • The correlation ID

send() returns a boolean — true on successful delivery, false on timeout.

What does MessagingTemplate.receive() return when the queue is empty and the timeout expires?

  • An empty Message with a null payload
  • null
  • false
  • It throws an exception

receive() returns null when no message is available within the receiveTimeout. It does not throw.

What is the default value of sendTimeout and receiveTimeout?

  • 5000 (5 seconds)
  • 1000 (1 second)
  • 0 (non-blocking)
  • -1 (block forever)

Both default to -1, meaning the template blocks indefinitely. Always set explicit timeouts in production code.

How does the handler in a sendAndReceive flow send its reply back?

  • It calls template.send() on a known output channel
  • It sends to the channel stored in the replyChannel header
  • It returns the value from the handler method
  • It publishes to the global error channel

The handler extracts the replyChannel header from the incoming message and sends the reply there. This is the return address EIP.

Which channel sub-interface does receive() require?

  • SubscribableChannel
  • MessageChannel
  • PollableChannel
  • DirectChannel

receive() requires a PollableChannel because you can only pull messages from a pollable (queue-backed) channel. Sending works with any MessageChannel.

What EIP concept does sendAndReceive's temporary channel mechanism implement?

  • Wire Tap
  • Message Filter
  • Content Enricher
  • Return Address

The temporary anonymous reply channel is the Return Address EIP — the sender tells the receiver where to send the reply via a header.

Can you use MessagingTemplate.send() with a PollableChannel?

  • Yes — send() accepts any MessageChannel
  • No — send() only works with SubscribableChannel
  • Only if a poller is configured
  • Only with QueueChannel, not PriorityChannel

send() accepts any MessageChannel (the root interface), including PollableChannels. It's receive() that is restricted to PollableChannel.
