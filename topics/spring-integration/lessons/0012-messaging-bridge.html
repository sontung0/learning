Messaging Bridge

A trivial endpoint that connects two channels — the simplest way to join a PollableChannel to a SubscribableChannel (or vice versa).

Why this lesson exists

A messaging bridge is the simplest endpoint in Spring Integration. It forwards every message received on its input channel to its output channel, with zero transformation. Conceptually it's just a BridgeHandler — a handler that calls outputChannel.send(message) [ref].

The bridge is most useful for connecting a PollableChannel to a SubscribableChannel. The bridge manages the polling configuration, so downstream subscribers don't need to know about the queue. This also enables throttling: the poller's trigger and maxMessagesPerPoll control the rate at which messages flow through.

Mission tie-in: The bridge completes the "how do I connect things" trilogy: channel adapter (on-ramp/off-ramp), poller (scheduler), bridge (connector). Understanding all three gives you complete control over how messages enter, move through, and leave your integration flows.

1. @BridgeFrom and @BridgeTo

The simplest way to create a bridge is with @BridgeFrom on the target channel bean [ref]:

@Bean
public PollableChannel sourceChannel() {
    return new QueueChannel();
}

@Bean
@BridgeFrom(value = "sourceChannel",
            poller = @Poller(fixedDelay = "500", maxMessagesPerPoll = "1"))
public SubscribableChannel bridgedChannel() {
    return new DirectChannel();
}

This creates a BridgeHandler that polls sourceChannel every 500ms and forwards each message to bridgedChannel. The handler itself then subscribes to a downstream subscriber (a @ServiceActivator).

Alternatively, @BridgeTo goes on the source channel bean and names the target:

@Bean
@BridgeTo(value = "bridgedChannel",
          poller = @Poller(fixedDelay = "500", maxMessagesPerPoll = "1"))
public PollableChannel sourceChannel() {
    return new QueueChannel();
}

2. BridgeHandler (@ServiceActivator)

You can create a bridge programmatically with BridgeHandler directly [ref]:

@Bean
@ServiceActivator(inputChannel = "sourceChannel",
                  poller = @Poller(fixedRate = "500", maxMessagesPerPoll = "1"))
public BridgeHandler bridgeHandler() {
    BridgeHandler bridge = new BridgeHandler();
    bridge.setOutputChannel(targetChannel());
    return bridge;
}

This gives you full control — you can set the output channel programmatically, configure it to use the reply channel from the message headers, or attach interceptors.

3. Java DSL bridge

In the Java DSL, the bridge is a flow step [ref]:

@Bean
public IntegrationFlow bridgeFlow() {
    return IntegrationFlow.from("sourceChannel")
            .bridge(e -> e.poller(Pollers.fixedDelay(500).maxMessagesPerPoll(1)))
            .channel("targetChannel")
            .get();
}

The .bridge() step is equivalent to .handle(new BridgeHandler(), ...) — it's just syntactic sugar for readability.

4. Use cases

  • Pollable → Subscribable: The primary use case. A QueueChannel with poller feeds a DirectChannel that downstream subscribers can use without polling concerns.
  • Throttling: The bridge's poller controls message throughput. maxMessagesPerPoll="10" with fixedRate="5000" limits to 10 messages every 5 seconds.
  • Connecting channel adapters: Bridge stdin to stdout (<int-stream:stdin-channel-adapter> → <int:bridge> → <int-stream:stdout-channel-adapter>), or file to JMS, mail to file, etc.

If no output-channel is specified, the bridge uses the reply channel from the incoming message header (if one exists). If neither is found, an exception is thrown.

Key takeaways

  • Messaging Bridge is a zero-transformation endpoint that forwards messages from one channel to another.
  • Primary use case: bridge a PollableChannel to a SubscribableChannel so downstream subscribers don't need polling configuration.
  • Throttling: the bridge's poller controls throughput via maxMessagesPerPoll and trigger configuration.
  • Three configuration styles: @BridgeFrom/@BridgeTo, BridgeHandler + @ServiceActivator, Java DSL .bridge().
  • If no output channel is specified, the bridge uses the reply channel from the incoming message header.
