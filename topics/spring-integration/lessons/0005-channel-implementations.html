Message Channel Implementations

Seven channel types in the framework, their interface branch, dispatch behaviour, and when to use each.

Why this lesson exists

Lesson 0004 taught you the interface contracts. This lesson teaches you the concrete implementations — the seven channel classes Spring Integration ships — and the practical trade-offs that make you pick one over the other in a real flow [ref].

Mission tie-in: Choosing the right channel type is the single most impactful design decision in a Spring Integration flow. Use the wrong one and you'll fight thread-pool exhaustion, transaction boundaries, or back-pressure for the rest of the project. Know them all and the choice becomes trivial.

1. DirectChannel — the default

The channel you reach for 80% of the time. It is the default when you declare a channel without a <queue> element [ref]:

// Simplest form — this is a DirectChannel:
@Bean
public MessageChannel orders() {
    return new DirectChannel();
}
  • Point-to-point: each message goes to exactly one subscriber.
  • Synchronous: the caller's thread invokes the MessageHandler directly. No thread handoff means a single transaction can span both sides.
  • Load balancing: when multiple handlers subscribe to the same DirectChannel, the dispatcher uses round-robin by default. You can switch to load-balancer="none" for fixed-order failover.
  • Failover: enabled by default. If handler A throws an exception, the dispatcher tries handler B. Set setFailover(false) to fail fast.

Because there's no buffering, send() blocks the caller until the handler returns. For fast in-process flows this is exactly what you want — for slow handlers, it pins the sender's thread.

Dispatcher configuration

DirectChannel channel = new DirectChannel();
channel.setFailover(false);           // stop on first exception (default: true)
channel.setLoadBalancingStrategy(null); // "none" — fixed order (default: round-robin)

2. QueueChannel — buffered, polled

A PollableChannel backed by a BlockingQueue. Messages are buffered until a consumer pulls them via a poller [ref]:

@Bean
public PollableChannel tasks() {
    return new QueueChannel(25);  // bounded — essential in production
}
  • Capacity: unbounded by default (new QueueChannel()). Always set a capacity in production — an unbounded queue can exhaust memory under load.
  • Send behaviour: if space is available, returns immediately. At capacity, the sender blocks until space frees or the send() timeout elapses.
  • Receive behaviour: receive(-1) blocks until a message arrives; receive(0) returns null immediately if empty.
  • Requires a poller: without a PollerMetadata bean, nobody calls receive() and messages sit forever.
Always bound your QueueChannels. An unbounded QueueChannel looks convenient during development but is a production incident waiting to happen — a fast producer can fill the heap before you notice.

3. PublishSubscribeChannel — broadcast

Broadcasts every message to all subscribed handlers. Implements SubscribableChannel — no polling, no buffering [ref]:

@Bean
public MessageChannel events() {
    return new PublishSubscribeChannel();
}

// Async broadcasting via a TaskExecutor:
@Bean
public MessageChannel asyncEvents() {
    return new PublishSubscribeChannel(someExecutor());
}
  • Min subscribers: by default minSubscribers = 0. If you set it higher, send() returns false when fewer subscribers are registered.
  • Threading: without an executor, all handlers run on the caller's thread (sequentially). With an executor, each handler invocation is submitted independently and send() returns as soon as the minimum number of subscribers has been met.
  • Error handling: with an executor, exceptions can be caught by the configured error channel. Without an executor, an exception in handler #2 prevents handler #3 from running.

4. ExecutorChannel — async point-to-point

A point-to-point SubscribableChannel that hands off message dispatch to a TaskExecutor. The sender's thread is freed immediately [ref]:

@Bean
public MessageChannel asyncChannel() {
    return new ExecutorChannel(Executors.newFixedThreadPool(4));
}
  • Breaks the transaction scope: because the handler runs on a different thread, a transaction on the sender's side does not extend to the receiver.
  • Supports load-balancing and failover, same as DirectChannel.
  • The sender can still block if the executor's queue is full and its rejection policy is CallerRunsPolicy.

When to use: fire-and-forget flows, or when you need to decouple the producer's thread from the consumer's processing time.

5. PriorityChannel — ordered pollable

A PollableChannel backed by a PriorityBlockingQueue. Messages are ordered by the priority header (or a custom Comparator) [ref]:

@Bean
public PollableChannel priorityChannel() {
    return new PriorityChannel(10);
}
  • Messages with a higher priority header value are consumed first.
  • Like QueueChannel, requires a poller and can be bounded.
  • Can be backed by a persistent MessageGroupQueue for durable priority queues.

6. RendezvousChannel — synchronous handoff

A PollableChannel that uses a zero-capacity SynchronousQueue. The sender blocks until a receiver is ready, and the receiver blocks until a sender arrives [ref]:

@Bean
public PollableChannel rendezvous() {
    return new RendezvousChannel();
}
  • Ensures the sender knows the message has been accepted — no buffering, no dropping.
  • Useful when you need guaranteed handoff and the consumer cannot miss a message, but you don't want buffering.

7. FluxMessageChannel — reactive

A channel that bridges Spring Integration with Project Reactor. It implements ReactiveStreamsSubscribableChannel and acts as a hot Publisher [ref]:

@Bean
public FluxMessageChannel fluxChannel() {
    return new FluxMessageChannel();
}
  • Messages are sunk into a Flux — reactive subscribers consume them with back-pressure.
  • Neither SubscribableChannel nor PollableChannel — it's a third branch in the channel hierarchy.
  • Useful for reactive flows where you want to compose integration steps with Reactor operators.
